# PRD и техническое задание: сайт подбора рецептов по продуктам

## 0. Коротко о проекте

**Рабочее название:** «Что приготовить?»

**Формат:** веб-сайт, позже PWA/мобильное приложение.

**Главная идея:** пользователь вводит продукты, которые есть дома, а сайт подбирает блюда, которые можно приготовить полностью или почти полностью.

**Ключевая ценность:** не просто показать рецепты, а решить бытовую проблему: «Я открыл холодильник и не знаю, что приготовить».

---

# 1. PRD

## 1.1. Цель продукта

Создать сайт, который помогает пользователю быстро подобрать блюдо на основе имеющихся продуктов.

Продукт должен:

1. Принимать список продуктов пользователя.
2. Подбирать рецепты по степени совпадения.
3. Показывать, что можно приготовить прямо сейчас.
4. Показывать, каких продуктов не хватает.
5. Давать подробный рецепт с шагами приготовления.
6. Быть удобным на телефоне.
7. Легко расширяться новыми рецептами, фильтрами, авторизацией и AI-функциями.

---

## 1.2. Основной пользовательский сценарий

Пользователь заходит на сайт и видит главный экран:

> «Что есть дома?»

Он вводит продукты:

- курица
- рис
- яйцо
- сыр

Нажимает кнопку:

> «Подобрать рецепты»

Сайт показывает:

1. **Можно приготовить** — рецепты, где есть все основные ингредиенты.
2. **Почти подходит** — рецепты, где не хватает 1–2 ингредиентов.
3. **Можно заменить** — рецепты, где часть ингредиентов можно заменить.

Пользователь открывает рецепт, видит:

- фото блюда;
- время приготовления;
- сложность;
- список ингредиентов;
- чего не хватает;
- пошаговую инструкцию;
- советы по замене продуктов.

---

## 1.3. Целевая аудитория

### Основная аудитория

Люди 20–45 лет, которые регулярно готовят дома, но часто не знают, что приготовить из имеющихся продуктов.

### Сегменты

1. **Молодые люди и студенты**
   - хотят быстро и дешево приготовить;
   - часто имеют ограниченный набор продуктов.

2. **Семьи**
   - ищут идеи для завтрака, обеда, ужина;
   - хотят использовать продукты из холодильника, чтобы ничего не пропадало.

3. **Занятые люди**
   - мало времени;
   - нужны быстрые блюда за 10–30 минут.

4. **Люди, которые экономят**
   - хотят готовить из того, что уже есть;
   - не хотят каждый раз заказывать доставку.

---

## 1.4. Позиционирование

Не «сайт рецептов», а:

> Умный помощник, который говорит, что приготовить из продуктов, которые уже есть дома.

Основное отличие от обычных сайтов рецептов:

- пользователь начинает не с названия блюда, а со списка продуктов;
- сайт показывает не только точные совпадения, но и «почти подходит»;
- сайт объясняет, чего не хватает;
- сайт предлагает замены;
- сайт экономит время и продукты.

## 1.5. MVP: первая версия

Первая версия должна быть простой, но рабочей.

### В MVP входит

1. Главная страница.
2. Ввод продуктов.
3. Быстрые кнопки популярных продуктов.
4. Подбор рецептов.
5. Список результатов.
6. Страница рецепта.
7. База из 50–100 рецептов.
8. Адаптивная мобильная верстка.
9. Простая SEO-структура.

### В MVP не входит

1. Регистрация.
2. Личный кабинет.
3. Платная подписка.
4. Сложный AI.
5. Мобильное приложение.
6. Комментарии.
7. Пользовательские рецепты.
8. Интеграция с доставкой продуктов.

## 1.8. Логика подбора рецептов

Для MVP используем простой алгоритм.

### Данные пользователя

Пользователь вводит список продуктов:

```text
курица, рис, яйцо, сыр
```

### Данные рецепта

У каждого рецепта есть список ингредиентов:

```text
курица, рис, лук, морковь, соль, масло
```

### Что считаем важным

Не все ингредиенты равны.

Ингредиенты делятся на:

1. **Основные** — без них блюдо теряет смысл.
   - курица;
   - рис;
   - картофель;
   - яйца;
   - мясо;
   - рыба.

2. **Дополнительные** — улучшают вкус, но не всегда критичны.
   - зелень;
   - специи;
   - соусы.

3. **Базовые** — обычно есть дома, можно не учитывать строго.
   - соль;
   - перец;
   - вода;
   - масло.

### Формула подбора

```text
score = количество совпавших важных ингредиентов / количество важных ингредиентов рецепта
```

### Категории результата

1. **Можно приготовить**
   - совпадение основных ингредиентов 100%;
   - или не хватает только базовых/дополнительных продуктов.

2. **Почти подходит**
   - не хватает 1–2 важных ингредиентов.

3. **Не подходит**
   - не хватает больше 2 важных ингредиентов;
   - рецепт не показываем в первой версии.

### Сортировка

Сначала показываем:

1. 100% совпадение.
2. Меньше недостающих продуктов.
3. Меньше время приготовления.
4. Более простые рецепты.
5. Более популярные рецепты.

# 2. Техническое задание

## 2.1. Рекомендуемый стек

### Для первой версии

- **Next.js** — сайт и серверная логика в одном проекте.
- **TypeScript** — чтобы меньше ломать код.
- **Tailwind CSS** — быстрая и аккуратная верстка.
- **Local JSON / TypeScript data-файл** — база рецептов на старте.
- **Vercel** — деплой сайта.

### После MVP

- **Supabase / PostgreSQL** — нормальная база данных.
- **Supabase Auth** — регистрация.
- **Supabase Storage / S3** — картинки.
- **Meilisearch / PostgreSQL full-text search** — быстрый поиск.

---

## 2.2. Почему начинать без сложной базы

На старте лучше не усложнять.

Первая версия может хранить рецепты в файле:

```text
/src/data/recipes.ts
```

Плюсы:

- быстрее запустить;
- меньше ошибок;
- проще вайбкодить;
- проще проверить идею;
- потом можно перенести в Supabase.

## 2.6. Логика нормализации ингредиентов

Файл:

```text
/src/lib/normalizeIngredient.ts
```

Функция должна:

1. Приводить строку к нижнему регистру.
2. Убирать лишние пробелы.
3. Заменять «ё» на «е».
4. Приводить синоним к базовому названию.

Пример:

```text
"Картошка" → "картофель"
"помидоры" → "помидор"
"куриная грудка" → "курица"
```

---

## 2.7. Логика матчинга рецептов

Файл:

```text
/src/lib/matchRecipes.ts
```

Функция:

```ts
matchRecipes(userIngredients: string[], recipes: Recipe[]): RecipeMatchResult[]
```

### Алгоритм

1. Нормализовать продукты пользователя.
2. Для каждого рецепта нормализовать ингредиенты.
3. Разделить ингредиенты рецепта на:
   - essential;
   - optional;
   - basic.
4. Проверить совпадения.
5. Посчитать недостающие обязательные ингредиенты.
6. Посчитать score.
7. Присвоить status.
8. Отсортировать результаты.

### Правила статусов

```text
can_cook:
  missingEssentialIngredients.length === 0

almost:
  missingEssentialIngredients.length <= 2

not_enough:
  missingEssentialIngredients.length > 2
```

В MVP показываем только:

- can_cook;
- almost.

# 5. Инструкция по вайбкодингу

## 5.1. Где начинать

Лучший старт:

1. Установить **Cursor**.
2. Установить **Node.js LTS**.
3. Создать проект на **Next.js**.
4. Открыть проект в Cursor.
5. Вставить этот PRD как файл `PROJECT_PRD.md`.
6. Давать Cursor маленькие задачи, а не просить «сделай весь сайт».

---

## 5.2. Главное правило вайбкодинга

Нельзя писать ИИ:

> Сделай мне сайт рецептов.

Правильно писать:

> Создай компонент IngredientInput по требованиям из PROJECT_PRD.md. Компонент должен позволять добавлять продукты, удалять продукты и передавать список продуктов в родительский компонент.

То есть задачи должны быть маленькими.

---

## 5.3. Рекомендуемый порядок промптов

### Промпт 1. Создание проекта

```text
Создай структуру проекта для сайта подбора рецептов по продуктам на Next.js + TypeScript + Tailwind CSS.
Используй App Router.
Не подключай базу данных на первом этапе.
Рецепты пока будут храниться в src/data/recipes.ts.
Следуй требованиям из PROJECT_PRD.md.
```

### Промпт 2. Типы данных

## 5.5. Как контролировать ИИ

После каждого шага проверять:

1. Сайт запускается?
2. Нет ошибок в терминале?
3. Компонент делает только то, что нужно?
4. Не сломались старые функции?
5. Код не стал слишком сложным?

Если ИИ начинает переписывать половину проекта — остановить и дать точечную задачу.

# 6. Definition of Done для MVP

MVP считается готовым, если:

1. Пользователь может ввести продукты.
2. Пользователь может удалить продукты.
3. Сайт показывает рецепты по совпадению.
4. Рецепты делятся на «можно приготовить» и «почти подходит».
5. На карточке видно, чего не хватает.
6. Можно открыть страницу рецепта.
7. На странице рецепта есть подробная инструкция.
8. Сайт нормально работает на телефоне.
9. Есть минимум 50 рецептов.
10. Проект можно развернуть на Vercel.

---

# 7. Главные риски

## Риск 1. Мало рецептов

Если рецептов мало, пользователь часто будет видеть пустой результат.

### Решение

На старте добавить минимум 50 рецептов, потом быстро довести до 200.

---

## Риск 2. Плохая нормализация продуктов

Пользователь пишет «картошка», а рецепт содержит «картофель».

### Решение

Сразу сделать словарь алиасов.

---

## Риск 3. Слишком сложный старт

Если сразу подключать авторизацию, базу, AI и админку — проект может застрять.

### Решение

Сначала локальная база рецептов, потом перенос в Supabase.

---

## Риск 4. Неудобный ввод продуктов

Если пользователю сложно вводить продукты, он уйдет.

### Решение

Сделать быстрые кнопки популярных продуктов и автодополнение.

---
